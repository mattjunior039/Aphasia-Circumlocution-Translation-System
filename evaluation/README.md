# Word-finding evaluation

## Reproduce

Run `npm run benchmark:semantic` from the project root. The machine-readable results are in [semantic-report.json](./semantic-report.json); [lexical-report.json](./lexical-report.json) captures the lexical-only comparison. The [test fixtures](../tests/fixtures/benchmark.js) contain the original editorial descriptions and annotations.

The main set contains 240 descriptions over 80 concepts. There are 120 development clues and 120 held-out clues, split by concept rather than by paraphrase. No description is generated by copying a vocabulary field. The fixed split is intentionally auditable and must not be changed to improve a score.

**Important sampling limitation:** the 80 main target concepts expand beyond the original bank. The original bank therefore has 0% canonical-target coverage on this set. That is evidence of missing vocabulary, not a representative estimate of its accuracy on its familiar 41 words. The fairer ranking comparison is expanded lexical versus semantic retrieval using exactly the same expanded vocabulary.

There are also eight positive regressions, including three ambiguous descriptions, and five negative regressions. Ambiguous cases have sets of acceptable answers. Hit@6 means at least one acceptable answer appears in the first six; ambiguity-answer coverage separately measures how many annotated alternatives appeared. Neither is precision across all six suggestions.

## Recorded held-out results

| Engine | Top-1 | Hit@3 | Hit@6 | Mean reciprocal rank |
| --- | ---: | ---: | ---: | ---: |
| Expanded lexical | 72.5% | 81.7% | 88.3% | 0.791 |
| MiniLM + lexical/structured ranking | 79.2% | 95.0% | 96.7% | 0.867 |
| BGE + lexical/structured ranking | 79.2% | 93.3% | 99.2% | 0.869 |

The expanded bank covers every main benchmark target. Coverage is reported separately rather than hiding out-of-bank failures. The full report includes aggregate and development metrics and individual missed clues.

Both local semantic engines achieved Hit@6 on all eight positive regressions, excluded the explicitly forbidden apple/hungry suggestions, and abstained on the five labeled negative cases. Both achieved **83.3% ambiguity-answer coverage**, so retrieving one plausible alternative does not imply all reasonable alternatives are offered.

### Model selection

MiniLM achieved 74.2% development top-1 and 95.0% development Hit@6, versus BGE's 73.3% and 94.2%. With a smaller weight file, it is the current opt-in UI choice. That choice uses development evidence, not a claim that it beats BGE on every held-out metric.

| MiniLM-L6, q8 | 22,972,370 | 6,102,528 | Mean, normalized |
| BGE-small-en-v1.5, q8 | 34,014,426 | 6,102,528 | CLS, normalized; retrieval query prefix |

Vocabulary/model revisions, runtime, architecture, and native inference latencies are recorded in the report. Native Node inference timing is **not browser timing**; it excludes browser initialization and asset loading. Browser checks confirmed the key results with single-threaded WASM. A separate eight-clue desktop integrated-browser spot check measured roughly 24–83 ms per search including rendering; it is not a representative performance benchmark. No real mobile device or memory ceiling was measured.

## Acceptance status

- The 90% acceptable-answer Hit@6 target is met by both semantic encoders on this held-out set and the aggregate main set.
- The **80% top-1 target is not met**: held-out top-1 is 79.2%; aggregate top-1 is lower.
- The coverage target is met on this deliberately scoped dataset.
- All five negative regressions pass, but the set is too small to validate a general 90% abstention claim.
- General aphasic speech, diverse speakers, unrelated domains, broader negation, and low-end/mobile performance are not validated.

The app therefore remains **experimental**, with suggestions and optional clarification rather than authoritative answers or confidence percentages. Clinical efficacy has not been assessed.

## Cloud comparison

No cloud engine was run and no cloud accuracy, latency, or cost is claimed. The user chose to keep cloud disabled after reviewing the local results. The architectural comparison is:

- Local embedding retrieval: private query handling, repeatable indexing, larger local assets, and limited contextual reasoning.
- LLM-assisted interpretation: potentially better flexible-clue interpretation and clarification, but requires a consented provider, a backend for secrets, a budget, output validation, and measured reliability.

If later authorized, compare it on the same frozen set, report repeated-run variability, validate candidates against the vocabulary, and preserve the on-device alternative. Do not send personal words by default.
